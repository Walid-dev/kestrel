The gates

Four gates, left to right. Gate 1 is committed on main; each build gate is one branch, merged into main with a merge commit once I say GO. A gate starts only after the GO on the one before it. Every step is pushed after its own GO, so the work is always saved.

The structure

One Node process serves the app and runs the background work. Requests come in only through Tailscale Serve, which adds my login. Inside, routes call the apps' rules, the rules call the database, and the AI part stays self-contained: it talks to the model queue and to nothing else of kestrel's.

The folders, one job each:

src/server/ — the routes (Hono); main.ts opens the database and passes it in src/domain/ — each app's rules; the only writer to the database src/db/ — SQLite, numbered migrations, a copy before each migration src/ai/ — the model client and prompts; imports neither db nor domain src/platform/ — the data folder's paths and the settings src/shared/ — the zod shapes the web app shares web/ — the React app; imports only src/shared/ evals/ — labelled cases and scorers for each AI feature scripts/ — the guard, deploy, the launchd template, the model probe, made-up dev data .githooks/ — pre-commit and pre-push run the guard, then the check docs/ — the plan, this runbook, decisions, process, reviews

The steps

One card per commit. Files lists what the commit adds or changes; each commit also updates this page's status. Check is how we know it worked, written so it can fail. At each GO card I read the changes and say GO.

The guard

builder

Before anything else can be committed, a short script runs on every commit: it refuses keys and passwords (through gitleaks), any staged file .gitignore covers, home paths with a user name, email addresses, phone-number shapes, and this computer's own user and host names, read when it runs (nothing written by hand); free-form personal details (an employer, a search's words) have no pattern, so they stay a rule for the builder and the reviews. Before every push, it does the same for the commits pushed, and refuses the old/* branches. It never prints what it found: only the file, and how to fix it. It needs no packages: Node runs the script directly, gitleaks is installed, and this step points git at .githooks (the toolchain step moves that into npm's prepare).

Files: .githooks/pre-commit · .githooks/pre-push · scripts/guard.ts · scripts/guard.test.ts

Check: git config core.hooksPath prints .githooks; node --test scripts/ passes with nothing installed; real commits are refused for a staged made-up key, a made-up email address, a made-up phone number and a home path with a made-up user name; the clean repo passes; a push of old/* is refused.

chore(guard): refuse keys, passwords and personal details in commits and pushes

Done. Proven with real commits: a made-up key, email, phone number, home path, the account's own name and a force-staged ignored file were each refused; the clean repo passes, and a push of old/* is refused. Two lessons from building it: gitleaks allowlists the documented EXAMPLE keys, so the key proof uses a random one; and the computer's names match as whole words of four or more characters, or a MacBook Pro's "Pro" refuses the word "project".

builder

10

The model client

builder

One small client for the computer's models, through the setup's model queue. It asks for an answer in a set shape (a JSON schema made from a zod shape), streams it, stops after a time limit that grows with the request, and never throws. It refuses a model not listed in my settings, and a request too long for the model, before calling. The domain records each call. A stand-in model answers in tests.

Files: src/ai/client.ts · src/ai/client.test.ts · src/ai/stand-in.ts · src/domain/calls.ts · src/db/migrations/004-model-calls.sql · src/platform/config.ts · scripts/probe-model.ts

Check: tests against a stand-in server: an answer in the wrong shape, a timeout and a refusal (the model declines) each become a failure with its reason, and an unlisted model is refused before any call. The probe, run by hand with made-up text, passes for Qwen and Ornith through the model queue.

Changes from the notes

builder

"Ask for changes" sends a set of one or more documents, and my notes, to the careful or the fast model. The code places each change in the original text only: where its text appears exactly once (or, when it repeats, inside or nearest its note's words); of two overlapping changes, the first. The rest are listed with the reason. The draft is kept until I save or discard it, and the screen checks on it every 2 seconds while it is being made. The review is a native dialog opened with showModal(), which Android's Back closes.

13

Save

builder

Save writes the real file, but only if its bytes haven't changed since the draft was made (another tool may have added to it). It writes next to the real file and swaps it in, keeping its permissions, encoding and line endings. The previous version is kept once, in the database, for Undo. The notes the draft answered move to Done. The review says which file Save writes.

Files: src/domain/notes/save.ts · src/domain/notes/save.test.ts · web/notes/review.tsx

Check: tests prove that save writes the file, a file changed after the draft was made is refused with "changed since", and Undo brings back the previous text.
