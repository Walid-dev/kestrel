# v0.3 · Applications — the build plan

Auto mode: plan, adversarial plan review, build with checks, multi-lens sweep after. The promises: one page by
state, every stopped application counted; the apply agent starts from kestrel and reports back through kestrel
commands; human checks on the phone or at the computer with my OK never counting as passed; kestrel tells me on the
phone when something needs me, and Home shows what needs me and what runs now, live.

## The shape

Kestrel owns the queue and the record; the agent (today: the chat app's apply agent) stays the hands. The bridge is
a small CLI speaking to the loopback API with the computer's own login, so the agent needs no new credentials. The
phone learns live through one server-sent events stream — the service worker has never cached `/api/events` since
v0.1, by design, for exactly this.

## The steps

1. **The applications table and states** — migration: `applications` (id, listing, link, title, org, state, reason,
   agent, started, updated) with states `queued → applying → sent | not-sent | needs-me`; `not-sent` always carries
   its reason and offers Retry (back to queued); `needs-me` carries what it waits for (a check's kind and words).
   Counting is by state, whatever the listing's own status. Check: a state table test — every lawful move, every
   unlawful one refused with the reason.
2. **The doors for the agent** — POST `/api/apply/queue` (a listing id or a link), POST `/api/apply/claim` (the next
   queued becomes applying and comes back as the job to do), POST `/api/apply/report` (sent, not-sent with reason,
   needs-me with what it waits for), GET `/api/apply` (the lists by state and the counts). Writes are same-computer:
   the CLI reads the login from the data folder's settings and sends it, like Serve would. Check: route tests through
   the whole flow.
3. **The `kestrel` command** — `scripts/kestrel-cli.ts`, one small program the agent calls: `kestrel apply-queue
   <link>`, `kestrel apply-claim`, `kestrel apply-report <id> --sent | --not-sent "<reason>" | --needs-me "<what>"`.
   Plain JSON out, plain errors, exit codes the agent can read. Check: the CLI against a running dev server.
4. **Live events** — GET `/api/events`, server-sent: one stream carrying {kind, state, count} on every application
   change. Home gains a live strip (what needs me, what runs now) and the Applications screen updates without
   reloading. The installed app raises a phone notification (Notification API) when something lands in needs-me while
   it is open; a push service that leaves the computer stays rejected — local first, recorded. Check: an EventSource
   test sees a change land; the strip proven in the browser.
5. **The Applications screen** — one page by state: queued, applying, needs me (with what it waits for), sent, and
   not sent with its reason and Retry. A listing card in Searches gains "Queue to apply". Check: phone and computer
   widths on made-up data; the counts match the table.
6. **The cutover note** — the old apply flow stops the day kestrel's starts, so no job gets two applications:
   operational, recorded in the runbook when it happens. Until then the agent keeps its old flow; the bridge waits.

## Out of scope

The apply agent itself (it lives in the chat app for now); reCAPTCHA mechanics (the agent's side); deals.
