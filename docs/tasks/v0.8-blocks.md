# v0.8 · One set of blocks for every page, and tools for the agents — the proposal

**Status: GO (2026-11-23). Steps 1 to 3 are built (see "Built"); step 4 waits for a second program to ask.**

## The question

Every agent in kestrel should write answers that are easy to read and to learn from: code in colour, a diagram, a
comparison, a table, a quiz check. Should that be an MCP server, MCP tools, or plain tools inside kestrel?

## What the field does (searched 2026-11-23)

- **The model describes, the app draws.** The current practice is "declarative generative UI": the model writes a
  small structured description (JSON) that names components from a catalog the app owns; the app checks it against a
  schema and draws it with its own components. The model never writes HTML or React. Google's A2UI protocol works
  this way (a catalog as the trust boundary), as do LangChain's declarative generative UI and json-render.
- **Check every block, and degrade.** A block is untrusted input: it is checked against its schema before it is drawn,
  and one that fails shows as plain words. Clear descriptions of each component in the prompt are what make models
  use them well.
- **MCP is for sharing tools between programs.** For one app's own agents, plain function tools are the default;
  an MCP server earns its keep when a second program needs the same tools (dsh, Claude Code, OpenCode). The MCP Apps
  extension (interactive views in a chat host's iframe) is for hosts such as Claude Desktop, not for an app that draws
  its own pages.

## Today

- Lessons, Research reports and the quiz's explanations already share Learn's blocks (`web/src/learn/blocks.tsx`).
- Ask writes Markdown, plus two drawings (a flow, a comparison) and its own find and change blocks.
- Search lives in two places: Research and the deep checks use the model door's web search and page reader.

So the pieces exist, but each surface has its own set.

## The proposal

1. **One catalog of blocks**, one schema and one renderer for every surface (lessons, Research, the quiz, Ask, the
   writing review): text, heading, points, steps (the vertical flow), code with its language, table, compare, tree, a
   timeline, a small chart from numbers, a callout, an example, terms with their meaning, a check to answer, a source,
   and a link to an image or a video (the Mac's models make neither; a link to a good one is what they can give). The
   catalog's descriptions are written once and go into every prompt that writes blocks; an eval per block kind checks
   that both local models use it when it helps and leave it out when it doesn't.
2. **Diagrams the page lays out itself.** The model names the parts (steps, a tree's branches, a timeline's dates);
   kestrel's components place them. No free coordinates, no auto-layout library: Learn's hand-placed diagrams stay
   for lessons.
3. **One set of read tools for every agent in kestrel**: find in the page's data (built per app for Ask), read one
   lesson, note or listing by its id, search the web and read a page (the door's own tools, as Research uses them).
   Plain functions inside kestrel, one registry, the same for Ask, Research and the deep checks.
4. **MCP later, and thin.** When dsh's agents or Claude Code need kestrel's data, the read tools go out through the
   `kestrel` command first and a thin MCP adapter over it, as the setup's rule says (commands first, MCP as an
   adapter). Not for drawing.

## The steps, on a GO

1. The catalog: merge Ask's parts and Learn's blocks into one schema and renderer; Ask writes blocks. Eval.
2. The new kinds: tree, timeline, small chart, check, video link. Eval each.
3. The read tools' registry, used by Ask, Research and the deep checks.
4. The `kestrel` read commands, then the MCP adapter, when a second program asks.

## Built (2026-11-23)

- **The catalog**, `src/shared/blocks.ts`: seven kinds (flow, compare, tree, timeline, chart, callout, check), each
  with when it helps, its shape, and a tolerant reader. A drawing missing what it needs reads as nothing, and the
  page shows its words instead. Plain TypeScript readers, not zod: the web reads the same file, and zod would add
  its weight to every page.
- **One renderer**, `web/src/drawing.tsx`, for Ask's answers, Research's reports and the lessons (Learn's own block
  renderer hands the catalog's kinds to it).
- **The prompts read the catalog**: Ask's lists all seven as fenced blocks (prompt v4); Research's report lists the
  five drawings as typed blocks (v3). Markdown keeps text, lists, code and tables, which the models already write
  well.
- **Left out for now:** the image and video link. The Mac's models invent addresses when they write from memory;
  Research's sources already link the pages read.
- **The read tools** (step 3), `src/domain/ask/tools.ts`: read one item by its id (a lesson, a listing, a document),
  search the web, read a page. Each says when it helps and its shape; Ask's prompt lists the ones its page allows
  after the page's own find, and Ask's loop runs them (two rounds, three looks a round). Learn, the quiz, Searches and
  Research allow the web; Notes, Writing, Applications and Tasks read only, so nothing of mine goes into a search.
  Research and the deep checks keep their fixed steps and call the same web functions.
- **The eval**, `evals/blocks/`: nine questions, one per kind and two that need no drawing; the stand-in run is
  inside the check, the live runs are in `docs/eval/`.
