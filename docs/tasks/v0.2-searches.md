# v0.2 · Searches, jobs first — the build plan

**Status, 2026-11-21:** built and live. The Models screen switches door-validated picks; the engine ran a real
search on the deployed app (60 found, 52 new, 8 deduped against the import, no problem); the import landed 2,072
unique listings from the old setup's 2,075 (its own three duplicates collapsed, every hand status preserved); the
side-by-side is running — the old setup keeps the browser scripts and the job search, kestrel mirrors after each of
its rounds (nightly until 2026-11-24); its generic wrapper is retired (2026-11-24). The cutover (one final import, old
timer off, real job collectors on) closes the version. A multi-lens code review sweep follows in auto mode; findings
land as fix commits.

Auto mode (docs/process.md, 2026-11-21): built round after round without per-step GOs, pushed continuously; reviewed
per version by orchestrated agents and at the end by a second model over the whole repo.

## The shape

Kestrel owns the searches — the specs' store, the runs, the listings, the scores, the limits, the reporting. The
per-site collector scripts and the search terms stay in the data folder: they are personal (what I hunt and where)
and they break often, so the repo holds a generic engine and the data folder holds my sites. Kestrel speaks the old
setup's collector convention (a script that prints items as JSON; exit code 3 means the site wants a login; a check
mode answers without loading a page), so the existing scripts work unchanged.

## The steps

0. _(Already built while this plan was reviewed: the Models screen's picks make the effective model pair, so the
   client's listed-models rule follows a switch — the review's first finding, fixed in `4d5448a`.)_

1. **Models screen** — `model_settings` in the database (one row per use: notes-careful, notes-fast, more later);
   GET/POST `/api/models`; the screen lists the door's models (loopback /v1/models) and the pick per use, one tap;
   drafts read the pick, settings stay the fallback. Check: switch a use, the next ask runs on it, the pick survives
   a restart.
2. **The tables and the vocabulary** (the version's load-bearing decisions, reviewed here, not improvised):
   - `listings`: id, search, source, link, dedupe, status, starred, found, updated, score, match, data (JSON with the
     rest: title, org, location, pay, posted, excerpt, why, parts — the old setup's shape, so the import is lossless).
     `UNIQUE (search, dedupe)`; a run that meets a known dedupe or link updates lastSeen, never double-lists —
     including right after the import.
   - The dedupe key: the old setup's value travels on import; new items use normalized `org|title` (lowercase,
     punctuation out, spaces collapsed). The statuses are the old setup's vocabulary unchanged — new, interested,
     maybe, applied, interviewing, offer, rejected, passed (set aside), fake, closed — so the import maps one to one.
     (PLAN's "applied, failed, waiting" states are v0.3's applications table, not listing statuses.)
   - `starred` is three-valued: 1 starred by hand, 0 unstarred by hand, empty means automatic. **Priority** =
     starred, or an automatic great match that isn't passed or fake — so a great match stays through applied and
     interviewing, and leaves only by hand.
   - `search_runs`: id, search, started, ms, found, kept, problem. Zero found records "the page answered empty",
     never "nothing new".
   - The doors: GET `/api/search` (specs with their last run and problem), GET `/api/search/listings` (filters
     combine), POST `/api/search/listings/:id` (status, star), POST `/api/search/run/:id` (run now).
     Specs load from the data folder (`searches/*.json`), seeded made-up in dev.
     Check: tests on dedupe-not-duplicate (also right after an import), the Priority rule's table, the zero-is-a-problem
     rule, and run recording.
3. **The collector door, the whole contract** (the plan review's reality check): a collector runs with its own
   folder as the working directory (its runtime — node_modules, helpers — lives beside it in the data folder), the
   spec's `env` (the old convention's knobs: terms, pages, ages travel there) and the spec's own budgets
   (`limits.timeoutMs`, `limits.maxBytes`). Items carry structured pay (min, max, currency, **period** — an hourly
   wage is annualized before the floor). Exit 3 means "the site wants a login"; a browser script with no browser
   (`ECONNREFUSED …9222`, `connectOverCDP`) is its own problem kind — "the agent's browser isn't running" — never a
   cry-wolf "broken script" at boot; the agent's Chrome open with no window, and any other failure at its DevTools
   door, are named apart (2026-11-25). Its progress lines (stderr) feed Live's sentence for the run, counts only. **One
   run at a time, whoever asks**: the collectors share one computer and one browser tab, so the tick and Run now join
   the same line. Check: stand-in scripts exercise good, empty, broken, login-needed and browser-down runs; the line
   keeps two asks from interleaving.
4. **Scoring** — a generic rules engine configured by the spec: title words, skills, level, pay against a floor,
   cities and remote rules, freshness; score 0–100, match tier, the why in plain words. Check: a table of made-up
   jobs scores as labelled.
5. **The scheduler, sleep-proof** — a minute tick checks what is overdue instead of pointing at a wall-clock moment,
   so a computer that slept through the night catches up on wake: a spec runs when now minus its last run passes its
   `everyMinutes`; the database snapshots to `backups/` when no copy is younger than 20 hours, 7 kept. Check: tests
   with a fake clock prove the catch-up after a long sleep; a run on demand from the screen.
6. **The Searches screen** — opens on All; filters combine (state, source, match); Priority holds every great match
   and every starred job, through every status, until unstarred or set aside; aside folds away. Cards: title, org,
   place, pay, score with its why, posted, star, aside, the link out. Problems and last-run lines per search; a Run
   now button. Check: phone and computer widths in a real browser, on made-up data.
7. **The import, idempotent** — `node scripts/import-v1.ts --from <path>`: the import re-runs cleanly — a known row
   refreshes, nothing double-lists. A listing I never marked in kestrel follows the old database's status, star and
   note; since 2026-11-25 a mark made in kestrel (a stage, a star, a note, a delete) stays kestrel's, and only the old
   setup's own stages still arrive over it (decisions.md).
   The field map: id, hunt→search, link, dedupe_key→dedupe travel as they are; status keeps the old vocabulary; the
   data blob travels whole (star→starred three-state, score, match, matchWhy→why, appliedAt, notes and the rest stay
   readable inside data). The dry run prints counts by status **and the starred and scored totals**, both sides, so a
   wrong mapping cannot hide behind matching row counts. Check: a made-up old database proves dry, write, re-run-all-
   unchanged, and a source status change flowing in.
   7b. **The specs from the old setup** — `node scripts/convert-v1-specs.ts --from <path> --out <searches dir>` turns
   the old job_hunts rows into searches/*.json skeletons (name, title words, floor, deal-breakers → avoid), written
   to the data folder, `enabled: false` until each one's collector line is pointed at a real script. Check: a made-up
   job_hunts row converts; the real conversion at my machine.
8. **Side by side, without fighting over the browser** — during the week the old setup keeps driving the browser
   scripts alone; kestrel mirrors its results through the idempotent import, re-run by the scheduler after each of
   the old setup's rounds (nightly until 2026-11-24), and runs no job search of its own: its non-browser fetcher, the
   jobspy wrapper, was retired on 2026-11-24 (decisions.md). Search now on a job hunt the old setup runs starts the
   old setup's own, under its wait and limits, and the hunt reads as searching until the old setup's Live says it
   ended; the next mirror brings the finds (such a hunt shows no switch of its own). Before that deploy, a job spec in
   the data folder that points at the wrapper goes off or away. Two drivers on one logged-in browser tab would corrupt
   both judges' data, so kestrel's browser specs stay `enabled: false` until the cutover. **The cutover**: one final
   import (late statuses flow in), the old timer stops, kestrel's job searches get real collectors in the data folder
   and switch on — from then kestrel holds every listing alone. Recorded in the runbook when it happens.
