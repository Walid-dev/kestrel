# v0.2 · Searches, jobs first — the build plan

Auto mode (docs/process.md, 2026-11-21): built round after round without per-step GOs, pushed continuously; reviewed
per version by orchestrated agents and at the end by a second model over the whole repo.

## The shape

Kestrel owns the searches — the specs' store, the runs, the listings, the scores, the limits, the reporting. The
per-site collector scripts and the search terms stay in the data folder: they are personal (what I hunt and where)
and they break often, so the repo holds a generic engine and the data folder holds my sites. Kestrel speaks the old
setup's collector convention (a script that prints items as JSON; exit code 3 means the site wants a login; a check
mode answers without loading a page), so the existing scripts work unchanged.

## The steps

0. _(Already built while this plan was reviewed: the Models screen's picks make the effective model pair, so the
   client's listed-models rule follows a switch — the review's first finding, fixed in `4d5448a`.)_

1. **Models screen** — `model_settings` in the database (one row per use: notes-careful, notes-fast, more later);
   GET/POST `/api/models`; the screen lists the door's models (loopback /v1/models) and the pick per use, one tap;
   drafts read the pick, settings stay the fallback. Check: switch a use, the next ask runs on it, the pick survives
   a restart.
2. **The tables and the vocabulary** (the version's load-bearing decisions, reviewed here, not improvised):
   - `listings`: id, search, source, link, dedupe, status, starred, found, updated, score, match, data (JSON with the
     rest: title, org, location, pay, posted, excerpt, why, parts — the old setup's shape, so the import is lossless).
     `UNIQUE (search, dedupe)`; a run that meets a known dedupe or link updates lastSeen, never double-lists —
     including right after the import.
   - The dedupe key: the old setup's value travels on import; new items use normalized `org|title` (lowercase,
     punctuation out, spaces collapsed). The statuses are the old setup's vocabulary unchanged — new, interested,
     maybe, applied, interviewing, offer, rejected, passed (set aside), fake, closed — so the import maps one to one.
     (PLAN's "applied, failed, waiting" states are v0.3's applications table, not listing statuses.)
   - `starred` is three-valued: 1 starred by hand, 0 unstarred by hand, empty means automatic. **Priority** =
     starred, or an automatic great match that isn't passed or fake — so a great match stays through applied and
     interviewing, and leaves only by hand.
   - `search_runs`: id, search, started, ms, found, kept, problem. Zero found records "the page answered empty",
     never "nothing new".
   - The doors: GET `/api/search` (specs with their last run and problem), GET `/api/search/listings` (filters
     combine), POST `/api/search/listings/:id` (status, star), POST `/api/search/run/:id` (run now).
     Specs load from the data folder (`searches/*.json`), seeded made-up in dev.
     Check: tests on dedupe-not-duplicate (also right after an import), the Priority rule's table, the zero-is-a-problem
     rule, and run recording.
3. **The collector door** — run a script with a time limit and a size cap, parse items (source, url, title, org,
   pay, location, posted), map exit 3 to "needs a login" recorded on the run; a jobspy fetcher is just a collector
   script in the data folder. Check: a stand-in collector script exercises good, empty, broken and login-needed runs.
4. **Scoring** — a generic rules engine configured by the spec: title words, skills, level, pay against a floor,
   cities and remote rules, freshness; score 0–100, match tier, the why in plain words. Check: a table of made-up
   jobs scores as labelled.
5. **The scheduler, sleep-proof** — a minute tick checks what is overdue instead of pointing at a wall-clock moment,
   so a computer that slept through the night catches up on wake: a spec runs when now minus its last run passes its
   `everyMinutes`; the database snapshots to `backups/` when no copy is younger than 20 hours, 7 kept. Check: tests
   with a fake clock prove the catch-up after a long sleep; a run on demand from the screen.
6. **The Searches screen** — opens on All; filters combine (state, source, match); Priority holds every great match
   and every starred job, through every status, until unstarred or set aside; aside folds away. Cards: title, org,
   place, pay, score with its why, posted, star, aside, the link out. Problems and last-run lines per search; a Run
   now button. Check: phone and computer widths in a real browser, on made-up data.
7. **The import** — `node scripts/import-v1.ts --from <path>` reads the old setup's job_listings into kestrel:
   dry run by default printing counts (by status and source) that must match, `--write` to land them; statuses, stars
   and scores carried. Check: the dry run on a made-up old database, counts proven; then the real run at my machine.
8. **Side by side** — both setups run for a week; kestrel's runs-and-problems view is the judge; then the old
   searches stop (sooner than two weeks: they run on a timer). Operational, recorded in the runbook.

## Out of scope
